# 评论区分层回复：部署与验收

这次增加了真实回复关系、评论点赞和每个账号单独保存的心碎折叠状态，需要更新云端。此前仅调整评论面板样式时无需部署的说明，不适用于这次功能更新。

## 配置顺序

1. 打开微信开发者工具 → 云开发 → 数据库，在当前 `campus-social-dev` 环境中创建两个集合（已有就不用重复创建）：

   | 集合名称 | 用途 |
   | --- | --- |
   | `square_reply_children` | 一级评论下的回复，以及回复对象之间的关系 |
   | `square_comment_states` | 每个账号对每条评论的点赞、心碎折叠状态 |

2. 两个集合的权限均设为“仅管理员可读写”。自定义规则为 `{"read": false, "write": false}`；客户端通过 `userService` 访问。

3. 只在 **`square_reply_children`** 新增下面这一个普通复合索引，选“非唯一”：

   - 索引名称：`children_by_root`
   - 在同一个索引内，按顺序添加：`postId` 升序、`rootId` 升序、`status` 升序、`sortKey` 升序。已有索引保留，不要重复创建同名索引。

   等待索引创建完成。`square_comment_states` 按确定的文档主键查询，不需要新增复合索引。之前四个广场索引继续保留。

4. 回到代码编辑器，右键整个 `cloudfunctions/userService` 文件夹 → **上传并部署：云端安装依赖**。需要包含最新的 `square.js` 和 `service.js`，不要只上传单个文件。

5. 重新编译小程序，关闭评论区再打开，或点击“重试”。原有 `square_replies` 评论保留为一级评论，原有数据不需要迁移或删除。

## 截图中的“服务暂时不可用”

这是云函数失败时旧版统一返回的提示，缓存中的评论仍会保留在画面中。新版会查询 `square_comment_states`；如果集合未创建，云端读取就会失败。CloudBase 对应的错误类别是 [`DATABASE_COLLECTION_NOT_EXIST`](https://docs.cloudbase.net/error-code/basic/DATABASE_COLLECTION_NOT_EXIST)。

代码已将评论相关的缺失集合错误单独返回为 `COMMENTS_STORAGE_NOT_READY`，界面提示“评论服务尚未配置完成，请稍后再试”。这项错误分类也需要部署最新云函数才能生效。它不代表其他未知数据库或网络错误已解决。

如果上述配置完成后仍报错，在云开发 → 云函数 → `userService` → 日志中查看最新一次失败调用：缺失集合时日志会记录 `userService comments configuration: missing collection`。本地测试不连接云环境，不能替代这一步确认。

## 验收规则

- 每条评论、楼中回复的昵称行右侧都有两条杠菜单；本人的菜单为“删除评论”，他人的为“举报评论”，游客操作先登录。取消确认不提交，失败保留原评论。
- 删除一级评论后整组不再展示，动态回复总数扣除整组；删除楼中回复只删本条并扣减该组和动态数量，其他回复保留。重复删除不重复扣减，迟到查询和互动不能将其恢复。
- 举报选择原因并确认后，真实写入既有的 `square_reports` 集合（仍为仅管理员可读写），`targetType: comment`、`replyId`、`rootId`、`commentContent` 用于区分评论与动态举报；同一账号对同一评论去重。若此前没有创建 `square_reports`，先创建并设置 `{"read": false, "write": false}`。本次不增加复合索引，需重新部署整个 `userService` 后编译前端。
- 时间显示在评论正文下方。点击评论可指定回复对象，底部显示“回复 昵称”，可取消并改为评论动态。
- 已有回复默认折叠；最前两个未折叠评论组可在后台预取，点击“展开 N 条回复”复用新鲜缓存或在途请求，较多回复按页读取。
- 原本零回复的评论：新回复直接显示，并出现“收起”；收起后再点击展开可恢复。
- 原本已有回复的评论：旧回复维持折叠，本次新回复单独显示在“展开 N 条回复”按钮上方；不重复插入到已展开列表。
- 同组“展开”与“收起”互斥：旧回复仍折叠时仅显示“展开”；整组已展开，或原本没有旧回复且本次新回复直接显示时，才显示“收起”。
- 关闭评论区再打开，本次临时显示规则结束，所有已有回复恢复默认折叠。
- 爱心记录真实点赞，可以取消，重复提交和并发请求不会虚增数量。
- 对已心碎折叠的评论点击爱心，会在同一事务中恢复可见并设为已点赞；原本已点赞时只恢复，不重复增加数量。此规则同时适用于一级评论和子回复，需重新部署 `userService` 并编译前端；无需新建集合或索引。
- 心碎只保存当前账号的折叠状态。一级评论折叠后用感叹号与“该评论已折叠”替代正文，并隐藏整组回复；再次点击恢复。折叠子回复时，其后续回复也隐藏，其他同级回复保留。切换账号后互不影响。
- 未登录可以阅读；回复、点赞与心碎操作需要登录。普通未认证账号可参与。
- 发送失败保留文字和回复对象，重试不会重复写入。切换账号或离开页面，迟到响应不得恢复旧账号数据。
- 详情页与底部评论面板共用胶囊输入栏：空闲时显示当前账号头像和图片、贴纸、GIF 三个 SVG；聚焦后隐藏头像，输入文字后隐藏工具图标并显示蓝色圆形上箭头发送键。清空文字恢复工具图标，回复对象仍只显示在输入框上方。
- 图片、贴纸、GIF 仅展示图标，暂不接入上传或表情功能；不展示双箭头扩展按钮。本次输入栏调整只需重新编译前端。

本地检查：`node --test`。本次未代为部署云函数或创建云端集合。

## 评论响应速度优化（2026-11-18）

这次同时修改前端与云函数：**右键整个 `cloudfunctions/userService` → 上传并部署（云端安装依赖），然后重新编译小程序**。不新增集合、索引或权限，原有评论集合及索引继续使用。

- 评论点赞、取消、心碎、恢复先即时绘制，再后台保存。同一评论的两个状态共用队列，连续操作只保留最新目标，失败回退到最近一次确认结果。后台旧列表、其他待处理响应及换账号不能覆盖当前选择。只更新发生变化的评论组，减少整组列表重绘。
- 评论列表及已读楼中回复复用一分钟会话缓存；后台最多预取前两个有回复且未被心碎折叠的评论组，用户仍需手动展开才显示。展开合并正在进行的请求，不给每一条评论创建网络请求，缓存过期时保留已有内容。
- 发送立即在正确的一级评论或楼中位置显示“发送中…”；暂存行不进入真实缓存，不显示成功提示、不把待发送数量写入数据库。通过文字校验并确认事务后替换为正式评论；失败移除待发送行、恢复原文、原回复对象和同一提交标识，重试不会重复发送。
- 云端独立读取并行执行，作者资料按主键批量查询并仅在本次请求内复用；个人折叠状态与资料并行获取。点赞/心碎直接返回成功事务内确认的数据，省去提交后的重复读取；发布回复后的评论、根评论和动态并行读取并组合展示。仍检查真实账号、动态与评论是否可见，学校认证不作为广场互动门槛。

事务成功后使用本次回调捕获的快照，不依赖 SDK 是否将返回值包裹在 `result` 中；只在 `await runTransaction` 确认提交成功后使用，失败不返回成功快照。同一事务内顺序读取，独立的事务外查询仍并行执行。微信 SDK 和 CloudBase SDK 的返回形态不能直接混用，参考[微信 SDK 的事务适配源码](https://github.com/wechat-miniprogram/wx-server-sdk/blob/master/index.js)及[CloudBase Node SDK 的回调返回示例](https://github.com/TencentCloudBase/node-sdk/blob/master/docs/database/database.md)。文字校验仍在事务前完成，服务端通过审核及事务提交后才算发布成功；网络、冷启动和文字校验的实际耗时仍需在真实环境测量，不能承诺所有请求瞬间完成。

### “重新部署后仍提示服务暂时不可用”的兼容修正

已确认本地原实现存在事务返回结构假设：只在包裹结果测试中通过，直接返回回调值时在成功提交后取 `committed.result.row` 会抛异常。新增回归测试可复现相同通用错误提示，修正后兼容两种返回方式；还覆盖事务内逐条读取的适配场景。此缺陷可能造成数据库已经改变、客户端却误以为失败，不应因此删除评论或重复更换提交标识。

computer-use 检查确认用户当前环境已部署，但日志服务尚未开启，因此没有获得这次历史错误堆栈；不能将本地复现等同于线上根因已完全确认。需要部署修正版并在真实环境验证点赞及发送。修正不需要新集合、权限或索引。

复测应覆盖：慢网下快速点赞/取消、心碎后立即点赞恢复、保存失败回退、关闭后重开评论、展开缓存回复、发送一级与楼中回复、审核拒绝后恢复原文、失败重试不重复、切换账号及离开后的迟到响应。真机确认前需要加载新前端，并部署更新的云函数。

## 评论时间顺序

一级评论按 sortKey 降序查询，分页继续读取更早评论；楼中回复按 sortKey 升序查询，分页继续读取更晚回复。前端按对应顺序合并缓存、新发送和 AI 回复；同一根评论内的新旧回复在展开后合并按时间正序展示，不因回复变新而改变根评论本身的发送时间顺序。原有本次新回复独立可见、关闭后折叠、个人心碎规则保持。

此更新需要部署整个 userService 并重新编译。旧升序索引可保留；等值前缀固定、单个 sortKey 排序可利用反向遍历。参考 [CloudBase 索引方向说明](https://docs.cloudbase.net/model/data-index)。新建环境按一级评论降序、楼中回复升序配置，无需迁移或删除评论。
